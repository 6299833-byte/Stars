# Живые обои на ПК: на чём переписать, чтобы было быстро и легко

Документ отвечает на вопрос владельца: на каком языке и стеке переписать обои для Windows, чтобы они работали как можно быстрее и тратили меньше ресурсов. Учтены три монитора, 4K, ультраширокие экраны и смешанное масштабирование.

Автор: агент perf-architect. Дата: 24.10.2026. Код приложения не менялся.

**Метки у каждого числа:**

- **[И]** — измерено здесь (headless Chromium + Playwright, Linux, 4 vCPU Xeon 2,1 ГГц, WebGL через SwiftShader);
- **[С]** — взято из источника (список в конце);
- **[О]** — оценка: расчёт или инженерное суждение. Её нужно проверить на настоящем Windows-ПК.

Натив на 3×4K: ≈30–60 МБ ОЗУ, ≈0,3–0,4 ГБ видеопамяти, <1 мс CPU на кадр [О]. |

## 1. Как устроено сейчас и куда уходят ресурсы

`StarsDesktop.exe` (C# .NET 8 WinForms, self-contained) создаёт одно окружение WebView2 и по одному WebView2 на монитор (`desktop/engine/Program.cs`, `WallpaperWindow.cs`). В нём живут процессы:

| Процесс | Сколько | Что делает |
|---|---|---|
| StarsDesktop.exe (.NET) | 1 | трей, WorkerW, пауза, SQLite уведомлений, ICS |
| msedgewebview2 browser | 1 | менеджер |
| msedgewebview2 GPU | 1 | ANGLE → D3D11, композитинг, растеризация Canvas 2D |
| msedgewebview2 utility (network и т. п.) | 1–3 | |
| msedgewebview2 renderer | **по одному на монитор** [И: 3 страницы — 3 рендера + запасной; С: process model] | JS страницы (≈3 200 строк), V8, Blink |

Что рисует страница `solar-system.html` в каждом кадре на каждом мониторе:

- видимый Canvas 2D `#sky` размером W×H×DPR;
- три полноэкранных 2D-холста фона: `bgCanvas`, `bgClose`, `bgSun`. Исходные фото Rubin при этом всего 1600–1800 px в ширину [И];
- полноэкранный WebGL-холст `glc` с `preserveDrawingBuffer: true` (лишняя полноэкранная копия на каждый кадр [С: Khronos]) и полноэкранная цель `scene` для bloom плюс цели 1/4 и 1/8;
- `ctx.drawImage(glc)` — WebGL копируется внутрь 2D-холста каждый кадр;
- орбиты, звёзды, пояса и метки — Canvas 2D на CPU;
- процедурные текстуры планет считаются на CPU в JS, **отдельно в каждом мониторе** (1024², «Максимальное» — 2048²).

Итого **8–10 полноэкранных RGBA8-поверхностей на монитор**, то есть около 32–40 байт на пиксель экрана [О, по коду]. В эмуляции наклон по разрешению — **71 байт/пиксель** в GPU-процессе [И]. SwiftShader держит часть копий дважды, поэтому на настоящей видеокарте ожидаем примерно половину.

## 2. Измерения

Скрипты лежат в scratchpad сессии (`perf/measure.mjs`, `perf/prof.mjs`). Страница запускалась в режиме обоев `#wallpaper`. Мост WebView2 подменялся, поэтому работают сообщения `config`, `pause` и `feed`, как в StarsDesktop. Для замеров снят снимок `solar-system.html`: параллельно его правит другой агент.

**Чему можно верить.** SwiftShader эмулирует GPU на CPU, поэтому частота кадров (0–3 кадра/с) и загрузка GPU-процесса (100–330 % CPU) **не годятся** для выводов. Годятся:

- память процессов (PSS). При SwiftShader «видеопамять» лежит в ОЗУ GPU-процесса, поэтому его PSS — верхняя граница объёма GPU-буферов;
- время JS на основном потоке на кадр, разбитое по фазам;
- число вызовов Canvas 2D и WebGL на кадр;
- количество процессов.

### 2.1 Память по разрешению, один монитор, «Обычное», 30 кадров/с [И]

PSS в МБ, вид — общий план, после прогрева. Сумма включает browser, zygote, network, GPU и renderer.

| Экран (CSS × DPR → холст) | Мпикс | GPU-процесс | Рендер-процессы | JS heap | Всего Chromium |
|---|---|---|---|---|---|
| 1920×1080 ×1 | 2,07 | 281 | 141 | 38 | 477 |
| 2560×1440 ×1 | 3,69 | 408 | 124 | 34 | 586 |
| 3440×1440 ×1 (21:9) | 4,95 | 474–503 | 97–118 | 34 | 635–654 |
| 5120×1440 ×1 (32:9) | 7,37 | 631–665 | 91–124 | 33–39 | ≈800 |
| 3840×2160 ×1 (4K, 100 %) | 8,29 | 706–742 | 87–125 | 33 | 844–879 |
| 2560×1440 ×1,5 (4K, 150 %) | 8,29 | 685–725 | 97–122 | 33–37 | 830–887 |
| 4K, «Максимальное» (холст 5760×3240) | 18,66 | **944–1305** | 86–95 | **92–94** | 1075–1442 |

Выводы:

- память растёт линейно по пикселям: ≈134 МБ + 71 МБ/Мпикс в GPU-процессе [И];
- 4K при 100 % и при 150 % стоит одинаково, потому что одинаков физический холст [И];
- «Максимальное» на 4K в 1,8 раза дороже «Обычного» и втрое увеличивает JS heap (текстуры 2048²) [И].

### 2.2 Три монитора [И]

| Конфигурация | Рендер-процессы | GPU-процесс | Рендеры (PSS) | Всего Chromium |
|---|---|---|---|---|
| 3×2560×1440, как сейчас | 4 (3 + запасной) | 775–851 | 185–241 | ≈1,0–1,1 ГБ |
| 3×2560×1440, `--renderer-process-limit=1` | **1** | 722–795 | **106–120** | ≈0,9–0,97 ГБ |

Общий рендер-процесс экономит **80–120 МБ** PSS на трёх мониторах [И]. Если смотреть по RSS, которая ближе к «Памяти» в Диспетчере задач, разница — 523–574 против 206–219 МБ [И]. Цена: JS всех мониторов идёт в одном основном потоке, об этом в 2.3.

На паузе, когда цикл кадров просто выходит раньше (rAF 60 Гц), рендер-процесс всё равно тратит **10–16 % CPU контейнера** [И]. Холостой цикл кадров не бесплатен.

### 2.3 Время JS на кадр по фазам [И]

Замер на этом CPU (Xeon 2,1 ГГц). Настольный CPU уровня Ryzen 5 7600 или Core i5-13400 примерно в 2–2,5 раза быстрее на одном потоке [О].

Фаза `pumpTextures` — это генерация текстур с бюджетом 5–10 мс на кадр. Она идёт только в первые секунды после старта или смены вида, и в постоянный режим не входит.

| Фаза, мс/кадр | Общий вид, 1920×1080 | Общий вид, 3840×2160 CSS | Сатурн вблизи, 1080p | Земля вблизи, 1080p |
|---|---|---|---|---|
| орбиты, пояса, кометы (`drawOverview`) | **7,9–8,6** | **8,0–8,8** | 0,4–1,4 | 0,4–3,2 |
| звёзды (`drawStars`) | 0,8–1,2 | **2,5–3,0** | 0,8 | 0,9–1,0 |
| крупный план WebGL (`drawClose`) | — | — | 0,8–1,0 | 2,9 |
| WebGL → 2D (`drawImage(glc)`) | 0,1 | 0,1 | 0,1–0,2 | 0,1–0,3 |
| фон (`drawImage(bgCanvas)`) | 0,05 | 0,05 | 0,05 | 0,05 |
| **итого без текстур** | **≈9–10** | **≈11–12** | **≈2–3** | **≈4–5** |

Вызовов на кадр в общем виде, 1080p [И]:

- Canvas 2D: 4 300 `fillRect` и столько же новых строк `fillStyle`, 4 700 `lineTo`, 1 150 `stroke`, 13 радиальных градиентов;
- WebGL: 23 `drawArrays`, 26 `useProgram`, 145 `uniform1f`.

На 4K (CSS 3840×2160) — 6 100–10 200 `fillRect`, потому что звёзд в 4 раза больше: их число задаёт формула W×H/3500 [И].

Что это значит:

- на настольном CPU общий вид стоит ≈4–5 мс на кадр на монитор [О]. При 30 кадрах/с это 12–15 % одного ядра на монитор, на трёх мониторах — 35–45 % ядра, то есть 6–8 % шестиядерного CPU;
- это только основной поток. Сверху идут GPU-процесс (растеризация Canvas 2D, композитинг) и .NET-хост;
- в нативной версии орбиты — это один вершинный буфер, а звёзды — один инстанс-вызов. CPU на кадр уходит в доли миллисекунды [О].

### 2.4 Чего здесь не измерить

- Настоящую нагрузку GPU и частоту кадров на Windows.
- Объём StarsDesktop.exe (.NET WinForms на Linux не запускается).
- «Выделенную видеопамять» по процессам.

Это первый шаг Фазы 0 на ПК владельца, команды в разделе 7.

Ещё о мониторах:

- **Смешанное масштабирование** (например, 4K на 150 % рядом с 1440p на 100 %). Стоимость задаёт физический размер холста, а не CSS [И, таблица 2.1]. Отдельное окно на монитор — правильная схема. Одно окно WebView на все мониторы получает один DPI на всё окно и тратит пиксели на прямоугольник-обёртку. Если высоты мониторов разные или один из них портретный, теряется 20–40 % [О]. При 3×7680 px ширина превышает максимальный размер текстуры 16 384 [О].
- **144–240 Гц.** Обои не должны следовать частоте монитора. Сейчас rAF просыпается с частотой экрана, а кадр пропускается в JS: на 240 Гц это 240 пробуждений в секунду на монитор вхолостую. В нативе — свой таймер на 30 кадров/с и `Present` без ожидания вертикальной развёртки других мониторов.
- **«Максимальное» на 4K.** Суперсэмплинг ×1,5 по стороне даёт холст 5760×3240 (18,7 Мпикс). На трёх 4K это ≈2 ГБ видеопамяти, больше четверти карты на 8 ГБ, а на глаз разница минимальна. Это первый кандидат на отключение.

Откуда разница в ОЗУ между нативными вариантами [О]:

- **C++** — только код, CRT, D3D11 и пользовательская часть драйвера (часть её общая с другими процессами), плюс данные сцены;
- **Rust + wgpu** — плюс валидация и аллокатор wgpu. По умолчанию аллокатор берёт память крупными блоками, поэтому нужны `MemoryHints::MemoryUsage` и проверка;
- **C#** — плюс рантайм .NET, JIT и WinForms, ≈40–80 МБ. NativeAOT с WinForms официально не поддерживается.

Текст и панель:

- **D3D11** дружит с Direct2D/DirectWrite через общую DXGI-поверхность. Кириллица, цветные эмодзи из сообщений и ClearType работают без своего атласа глифов;
- **D3D12** требует D3D11On12;
- **wgpu** — свой атлас (glyphon/cosmic-text) и ручной фолбэк шрифтов для эмодзи.

Это главная причина выбрать D3D11, а не D3D12 или wgpu.

## 5. Почему именно C++ / D3D11

1. **Самый низкий предел по всем ресурсам.** Один процесс, одно устройство, текстуры планет и фона загружаются и генерируются **один раз** на все мониторы. Сейчас каждый монитор считает их сам.
2. **D3D11 — самый совместимый API на Windows 10/11.** Он работает на старых iGPU, на WARP по RDP, и у него минимальные накладные расходы на простых сценах. Этой сцене (десятки вызовов отрисовки на кадр) D3D12 ничего не даёт.
3. **Нужные куски Windows — родные для C++:** WorkerW, `Shell_NotifyIcon`, `MonitorFromWindow`, `GetDpiForMonitor`, DirectWrite.
4. **Предсказуемость для фонового процесса, который работает сутками:** нет GC и JIT.
5. **Rust дал бы то же самое плюс безопасность памяти и Android,** но дороже на 2–4 недели, слабее с текстом и рискованнее по стабильности API wgpu. Если нативный Android когда-нибудь станет приоритетом, вернуться к Rust + wgpu.

**Почему запасной вариант — C# + Vortice.** Если на C++ нет ресурсов или главное — срок, этот путь даёт **те же видеопамять и нагрузку на GPU**, то есть главный выигрыш. Хост уже написан и проверен в CI. Разница с C++ — десятки мегабайт ОЗУ и размер exe.

### Фаза 1 — нативный прототип (3–4 недели, C++/D3D11)

- Окно в WorkerW на каждый монитор, одно устройство, flip-model swapchain (`FLIP_DISCARD`, 2 буфера, `SetMaximumFrameLatency(1)`) и свой таймер на 30 кадров/с.
- Фон, звёзды, орбиты и одна планета с кольцами и bloom. Шейдеры переводятся из GLSL ES в HLSL.
- Проверить flip-model на дочернем окне WorkerW в Windows 10 22H2 и Windows 11 24H2. Если не работает — запасная схема `DXGI_SWAP_EFFECT_DISCARD` или DirectComposition.

**Приёмка:** 3×4K, класс D — ОЗУ процесса ≤ 60 МБ, видеопамять ≤ 350 МБ, CPU ≤ 1 %, GPU ≤ 10 %, старт до первого кадра ≤ 0,5 с.

### Фаза 2 — паритет сцены (4–6 недель)

- Все тела, кольца с частицами, Луна, кометы, зонды, метеоры, НЛО, вид «За пределами», переходы и тур.
- Процедурные текстуры — пиксельным шейдером на GPU один раз при старте. Сейчас это делает JS на CPU для каждого монитора.
- Сверка с веб-версией скриптом скриншотов на одинаковых `days` и параметрах камеры.

**Приёмка:** то же, что в Фазе 1, на полной сцене. Класс L, 3×1440p: GPU ≤ 35 %, CPU ≤ 2 %. Видимых различий со скриншотами веб-версии нет.

### Фаза 3 — хост и панель (2–3 недели)

- Перенести трей, меню, `config.json`, правила паузы, чтение `wpndatabase.db` (SQLite) и ICS (с RRULE) в C++.
- Панель «часы / встречи / сообщения» — на Direct2D/DirectWrite.
- WebView2 убрать из Windows-сборки. Веб-страница остаётся для Android и браузера.

**Приёмка:** exe ≤ 5 МБ. 3×4K: ОЗУ ≤ 80 МБ, видеопамять ≤ 400 МБ, CPU ≤ 1 %, пауза ≤ 0,1 % CPU. Смена мониторов и DPI на ходу проходит без утечек: 24 часа, рост ОЗУ ≤ 5 МБ.

### Фаза 4 — по желанию

- Кривые качества (30 и 60 кадров/с, масштаб рендера 0,75–1,0 для 8K).
- HDR-вывод.
- Общий код сцены с Android, только если тогда будет выбран Rust.

**Запасной путь** (C# + Vortice): фазы те же, Фаза 3 сводится к замене `WallpaperWindow` (≈1 неделя). Цели по ОЗУ: Фаза 1 ≤ 130 МБ, Фаза 3 ≤ 150 МБ. Остальные цели те же.

## 7. Как мерить на Windows (для шага 0.0 и приёмки)

```powershell
# память: Private Working Set и выделенная видеопамять, сумма по обоям
$p = Get-Process StarsDesktop, msedgewebview2 -ErrorAction SilentlyContinue
"{0:N0} МБ private" -f (($p | Measure-Object PrivateMemorySize64 -Sum).Sum / 1MB)
$ids = $p.Id
(Get-Counter '\GPU Process Memory(*)\Dedicated Usage').CounterSamples |
  Where-Object { $ids -contains [int]($_.InstanceName -replace '^pid_(\d+)_.*','$1') } |
  Measure-Object CookedValue -Sum | ForEach-Object { "{0:N0} МБ видеопамяти" -f ($_.Sum / 1MB) }
# CPU и GPU за 60 секунд
Get-Counter '\Process(StarsDesktop)\% Processor Time','\Process(msedgewebview2*)\% Processor Time' -SampleInterval 5 -MaxSamples 12
Get-Counter '\GPU Engine(*engtype_3D)\Utilization Percentage' -SampleInterval 5 -MaxSamples 12
```

Внимание:

- msedgewebview2 других программ (Teams, Outlook, виджеты) тоже попадёт в выборку. Фильтровать по родителю или по папке `--user-data-dir=...StarsDesktop\WebView2` в командной строке процесса.
- `% Processor Time` нужно делить на число логических ядер.

## 8. Риски

| Риск | Вариант | Что делать |
|---|---|---|
| Flip-model swapchain в дочернем окне WorkerW ведёт себя по-разному в разных сборках Windows | натив | проверить в Фазе 1 на 10 22H2 и 11 24H2, запасные схемы — blt-model или DirectComposition |

| `preserveDrawingBuffer: false` где-то полагается на старое содержимое `glc` | веб | сверка скриншотами, флаг легко вернуть |
| Ошибки памяти в C++ при работе сутками | C++ | ASan в CI, санитайзеры, тест на 24 часа в Фазе 3 |

| Расхождение веб- и нативной сцены (две кодовые базы) | натив | данные (тела, орбиты, кольца) вынести в JSON, общий для обеих, и сверять скриншотами в CI |
